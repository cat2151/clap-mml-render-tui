# ADR 0019: 調査 Stage は「受け入れ条件の外に主張を置かない」

- 状態: 採用（[0018](0018-page-replacement-clears-the-cache.md) の調査の事後分析から）
- 関連: [0011](0011-verification-and-baselines.md) / [0018](0018-page-replacement-clears-the-cache.md)

## 何の話か

引き継ぎ資料を 1 Stage ずつ subagent へ渡して自走させる進め方（`handoff-stages`）で、
**調査が 2 つ目の Stage で答えを出し終えていたのに、残りの Stage が惰性で走った。**
そして**資料に書かれた 1 つの未検証の一文が、直しを丸 1 日ぶん止めていた。**

その一文は「rollover で `daily/` を消すと『昨日の続きを鳴らす』使い方を壊す」。
裏取りは grep 2 回で済んだ（[0018](0018-page-replacement-clears-the-cache.md) の根拠 4 点）のに、
誰もやらなかった。**この主張についてだけ、資料に実測ログも grep 結果も 1 行も無かった**
（他のすべての主張には実測ログが付いていた）。

## なぜそうなったか（構造の側）

- **受け入れ条件の外に書かれた主張は、誰も検証しない。** 各 Stage の受け入れ条件には
  厳しい実測の規律がかかっているが、「候補だが採否は設計判断」という**余談**には何もかからない
- **ワークフローが「ユーザーへ渡す」を報酬にしている。** promise が 3 値
  （`NEXT-STAGE-OK` / `NEEDS-HUMAN` / `ALL-STAGES-DONE`）だと、
  **未検証の副作用を 1 つ書くのが、判断を手放す最も安い方法**になる
- **誰も再スコープできない。** オーケストレータは資料もソースも読まず、subagent の最終行しか見ない。
  subagent は 2 つ目の Stage に着手しない。**「残りはもう要らない」と言える立場の主体が 1 人もいない**
- **資料が唯一の通信路なので、誤りは訂正されず伝播する。** subagent は会話履歴を持たないので、
  誤った一文を全員が毎回読む。同じ文言が 2 か所に現れて「2 回書かれている＝確からしい」という外観まで得た

**これは repo の構造のせいではない。** daw crate は最大ファイルが `AGENTS.md` の 450 行規約に収まっており、
context を食ったのはコードではなく**資料**（Stage ごとの追記で、最後の subagent が読む資料は最初の 1.65 倍）。

## 決定（次に同種の調査をするときの規則）

### 1. 「消す／残す」を論じるときは、読み手を file:line で全部貼る

> 削除・掃除・保持を提案するときは、その対象を読む **production の呼び出し元を file:line で
> 全部貼る**こと。貼れないものは「壊れる使い方」として書いてはならない。

**この 1 項目だけで今回の誤りは発生しない。**
なお [0018](0018-page-replacement-clears-the-cache.md) の「共通の底へ置くと Resume が壊れる」も、
**呼び出し元を 2 つ開くだけ**で見つかったもの（事後分析自身が、この規則を守らずに同型の誤りを
犯し、あとから訂正した）。

### 2. 受け入れ条件の外に置く根拠のいる主張には `[未検証]` を付ける

候補表・「注意」・余談に書く主張は、どれかの Stage の受け入れ条件へ落とすか、
落とせないなら **`[未検証]` を接頭辞として付ける。**
→ `[未検証] 「昨日の続きを鳴らす」使い方を壊すかもしれない` と書かれていれば、設計制約には昇格しなかった。

### 3. 各 Stage の報告に「残り Stage の要否」を 1 行義務づける

> 報告の最後から 2 行目に「**残 Stage の要否: 全部必要 / Stage N,M は当初の問いにもう答えない**」を書く。
> 後者なら promise は `NEEDS-HUMAN: 残り Stage の要否確認` にして止まる。

**再スコープできるのは subagent だけ**（オーケストレータは資料を読めない）。
この 1 行があれば、総コストのおよそ 2/3 がユーザーへの 1 つの質問に置き換わっていた。

### 4. スコープは「最も安い十分な説明を 1 つ出す」で切る

今回のゴールは「3 つの疑いをそれぞれバグかどうか断定する」で、
**ユーザーの報告を説明するより広かった。** 3 つを対等に並べた時点で、
既に完全な説明が手元にあるにもかかわらず残りの Stage の実行が確定していた。

## 併せて守ること（既存の規律。今回も効いた／破って痛かった）

- **静的なコード読みだけで断定しない。** この repo は静的な読みで過去に複数回誤っている。
  実際に走らせてログを見る Stage を独立させること（今回、実アプリを走らせた Stage が
  「Resume の日も毎起動再現する」という新事実を出した）
- **ログだけを見ても出ない原因がある。出た音を録ること**（[0012](0012-live-clock-drift-is-absorbed-not-eliminated.md)）
- **`git checkout -- <file>` を破壊実験の巻き戻しに使わない。** 両 repo とも未 commit の変更を
  大量に抱えているので、他人の作業ごと消える。**破壊の前にファイルをコピーし、そのコピーから戻す**
- **domain ロジックを検証スクリプト側へ複製したら、Rust 側と結ぶテストを用意するか、
  複製しないで済ませる**（今回 5 つのルールが Rust と Python に二重化し、両者を結ぶテストが無い）
